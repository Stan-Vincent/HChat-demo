## 2. 分模块策略（不要一刀切）

| 模块 | 编码 | 为什么 |
|---|---|---|
| `Client/` | **UTF-8（全部）** | MinGW/g++ 默认按 UTF-8 读源文件；Qt 的 `QString` 从 `const char*` 构造**默认按 UTF-8 解析**，GBK 字节会显示成乱码 |
| `ChatServer/` `GateServer/` `StatusServer/` | **GBK（保持）** | MSVC 按本地代码页(936)解析 GBK，**本来就是对的**。转 UTF-8 反而要加 `/utf-8`，还会踩 spdlog/fmt 的坑（已用 `FMT_UNICODE=0` 规避） |
| `Start/*.bat` | GBK + `chcp 936` | Windows 控制台默认 936，改 UTF-8 会乱码 |
| `docs/` `test/` | UTF-8 | 无编译依赖 |

> **结论：后端不要转 UTF-8。** 这不是懒，是转了要连带改编译选项，收益为负。

## 3. 铁律

1. **改源码前先体检**：`python test/encoding_audit.py`，看清目标文件是 UTF-8 还是 GBK 再动手。
2. **GBK 文件只准 Python 字节补丁**（`decode('gbk')` → 改 → `encode('gbk')`）。
   用 Edit/Write 直接改会按 UTF-8 写回，中文全部变成 `U+FFFD`，且**不报错、只烂注释**。
3. **编码会漂移**：`usermgr.h`、`chatdialog.h` 曾因上述原因被腐蚀，已还原并确认为 UTF-8，
   别再当 GBK 处理。所以每次都要重新体检，不能凭记忆。
4. 写入后自检：`open(f,'rb').read().decode('gbk')` 能成功、且 `U+FFFD` 计数为 0。
