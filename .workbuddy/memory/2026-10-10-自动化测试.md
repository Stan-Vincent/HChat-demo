## ★ 脚本踩的坑（写这类测试必备）
1. **帧头是 2+2 字节，不是 4+4**：`HEAD_ID_LEN=2`、`HEAD_TOTAL_LEN=4`，
   服务端用 `short` + `network_to_host_short` 解析。我一开始按 `>II` 发，
   服务端日志出现 `msg_id is 0 / msg_len is 1005`，才反应过来。
2. **DB 里 `user.pwd` 存的是 `xorString` 之后的密文**，用户输入框里敲的是明文。
   例如明文 `123456` → xor(6) → `745230` = 库里存的值。脚本要先 `xor_string(明文)` 再发。
3. `recv()` 的长度判断要和 `unpack` 的字节宽度一致（我改 unpack 忘了改 `8 + length`，白跑一轮）。
4. Windows 上 `(./exe &)` 起的进程会随 bash 退出被杀 —— 要用 Bash 工具的 `run_in_background=true`。

## ★★ 崩溃复现与四层修复（这次是脚本自动跑出来的）
脚本第 6 个用例直接把服务端打挂，日志证据：
```
recv_msg id  is 1007
user SearchInfo uid is
[ GET  ubaseinfo_ ] failed        ← 走进了 GetUserByUid("")
（随后 std::stoi("") 抛 std::invalid_argument → terminate）
```

**四层修复（全部已在源码里，需用户编译 ChatServer 生效）**：
| 层 | 位置 | 改动 |
|---|---|---|
| 根因 | `LogicSystem::isPureDigit` | 空串直接 `return false`（原来 for 循环不进 → return true） |
| 入口 | `LogicSystem::SearchInfo` | 空输入直接回 `UidInvalid`，不查库 |
| **兜底** | `LogicSystem::DealMsg` | handler 调用包 `try/catch(std::exception&)`，任何处理异常都不再让进程崩 |
| 通用 | `utils.cpp/h` 新增 `safeToInt()` | `LogicSystem::GetUserByUid` 的 `std::stoi` 换掉（空串/非数字/溢出都返回默认值） |

## 静态扫描结论（ChatServer 全量）
`std::stoi/atoi/substr/front/back/数组下标` 全扫一遍：
- **唯一的崩溃点就是 `LogicSystem.cpp` 那一处 `std::stoi`**，已换掉
- 其他 handler 取参都用 `root["x"].asInt()` / `.asString()` —— **jsoncpp 的安全接口，类型不匹配返回 0/""，不抛异常**
- `CServer::ClearSession` 里的 `_sessions[session_id]->` 前面有 `find` 判断，安全
