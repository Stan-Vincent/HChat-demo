## 修复：选中后点气泡"外"不取消选中（仅点气泡内才消失）
用户确认灰色 bug 修好后，指出 UX 逻辑不符：左键选中后，目前只有点击**气泡内**才清掉选中；点击**气泡外**（背景/别的消息/昵称/头像/滚动条）会让选中区保持"淡橙色"不消失。正确逻辑：选中状态下，**任意位置左键单击都应取消选中**。

- 根因：Qt 的 QTextEdit 只在鼠标按下**落在本控件内**时才清选区；落在控件外时事件不会到达该 QTextEdit，选区残留。因我们给 Inactive 组设了 `#ff9a6b`（浅橙），所以残留选区显示为"淡橙色"。
- 修法：在 `ChatView` 装 `qApp` 级事件过滤器（不用滚动区/视口级过滤器——子 QTextEdit 会吞掉自身的 MouseButtonPress，事件不冒泡到父级过滤器，导致"点别的区域"清不掉）。过滤器在任意 `MouseButtonPress`(LeftButton) 且落点在消息列表内时，遍历所有 `ChatItemBase`→`findChildren<TextBubble*>()`→调 `clearSelection()` 折叠光标清选区。
  - `TextBubble::clearSelection()`：仅 `QTextCursor::clearSelection()`+`setTextCursor`，不动 focus/交互标志 → 仍能重新选中（基本操作保留）。
  - 仅对 LeftButton 生效，右键全选→左键取消的逻辑不变；落在 ChatView 外（会话列表/输入框等）不动，避免误清。
  - 过滤器 `return QWidget::eventFilter`（不吞事件），正常点击/拖选/双击选词都不受影响——按下先清旧选区，QTextEdit 再正常起新选区。

## 修复：发送消息输入框"粘贴不了"（CTRL+V 无反应）
用户反馈发送框（ui->chatEdit，即 `MessageTextEdit`）粘贴文字没反应。

- 根因：`MessageTextEdit::insertFromMimeData` 被写成了"只处理文件拖放，其它一律丢弃"——当 `getUrl(source->text())` 取不到文件 URL 时直接 `return`，**连 `QTextEdit::insertFromMimeData` 基类都没调**，于是普通文字/HTML/图片剪贴板粘贴全被吞掉（CTRL+V 完全不动）。`keyPressEvent` 对非回车键都委托基类，CTRL+V 标准路径正会走到这个函数，所以这是唯一拦截点。
- 修法：改用 Qt 标准 `source->hasUrls()` 判断"带文件/图片"（比旧代码在 `source->text()` 里找 `///` 的 hack 更可靠，且覆盖"资源管理器 Ctrl+V 粘贴文件"）；命中则 `insertFileFromUrl`（内部按图片/文件分流）；其余一律 `QTextEdit::insertFromMimeData(source)` 交还基类，普通文字粘贴恢复。删除了不再使用的 `getUrl()`（声明+定义）。
- 注意：图片经 Ctrl+V 走基类会以内联图元插进 QTextDocument，但 `getMsgList()` 靠 `mMsgList` 匹配，基类插入不会登记 → 这类粘贴图暂不能随消息发出（拖拽图片仍可发，走 `insertImages` 登记）。本次只修"文字粘贴不了"，图片 Ctrl+V 发送是另一处旧限制，未扩范围。
- 验证：`mingw32-make -j4` 0 error（仅 post-link `copy` Error 127 已知无害），exe 10:38 更新。

## 修复：发送的图片显示不全
用户截图反馈：输入框里的图片完整，发出去后在聊天区只显示一小块（被裁）。

- 根因：`PictureBubble::applyPixmap()` 用 `pix.scaled(PIC_MAX_WIDTH, PIC_MAX_HEIGHT, Qt::KeepAspectRatio)` 得到等比缩放后的 `scaled`，然后只更新了气泡（`this`）的 `setFixedSize`，但**没更新内部 `QLabel _lb` 的固定尺寸**。`initEmpty()` 里 `_lb` 被设成 `setFixedSize(160,90)` 且 `setScaledContents(true)`，于是 _lb 把缩放后的图片又抻回 160×90，而气泡被缩成 `scaled` 尺寸（通常比 label 小）→ 气泡只看得见 label 顶部/左侧一小块，图片被裁。
- 修法：在 `applyPixmap` 里补上 `_lb->setFixedSize(scaled.size())`，并 `_lb->setScaledContents(false)` 避免二次拉伸；同时把 label 背景从占位灰 `#f0f0f0` 改成透明，使圆角 pixmap 的透明角露出气泡底色（自己#ffd0b8/对方白），而不是占位灰。
- 验证：`mingw32-make -j4` 0 error（仅 post-link `copy` Error 127 已知无害），exe 10:57 更新。

## 修复：登录输错邮箱/密码却提示"参数错误"
用户反馈：输错密码或邮箱应提示"邮箱或密码不正确"，实际显示"参数错误"。

- 根因：客户端 `global.h` 的 `ErrorCodes` 只有 `SUCCESS/ERR_JSON/ERR_NETWORK`，不认识服务端的错误码；`logindialog.cpp` 的 `ID_LOGIN_USER` 回包处理里**任何非 SUCCESS 都一律 `showTip("参数错误")`**。而 `GateServer/LogicSystem.cpp` 的 `/user_login` 里 `CheckPwd` 失败时统一返回 `ErrorCodes::PasswdInvalid = 1009`（服务端故意不区分"用户不存在/密码错"，避免被枚举），所以无论邮箱错还是密码错，客户端拿到 1009 仍然显示"参数错误"。
- 修法：
  1. `global.h` 的 `ErrorCodes` 补齐服务端码（`PasswdErr=1006`、`EmailNotMatch=1007`、`PasswdUpFailed=1008`、`PasswdInvalid=1009`、`TokenInvalid=1010`、`UidInvalid=1011`、`DbErr=1012`），与服务端 `GateServer/const.h` 对齐。
  2. `logindialog.cpp` 登录回包：`error == PasswdInvalid(1009)` → `showTip("邮箱或密码不正确")`；其余仍走"参数错误"（保留其它服务端异常的兜底）。

## 修复：连续改备注后备注按钮卡死 + 退出再登录无限卡在加载
用户报告严重 bug：连续修改两次好友备注后，备注修改按钮（back_edit_btn）一直不可用；退出登录再登录会无限阻塞于加载状态。

### 根因（关键：备注按钮"卡死"是**模态加载框遮挡**的假象，不是按钮本身）
- `back_edit_btn->setEnabled(false)` 只在 `on_back_edit_btn_clicked` 发请求时置灰；`slot_update_back_rsp` **第一行就 `setEnabled(true)`**，且服务端 `ChatServer/LogicSystem.cpp::UpdateFriendBack` 用 `Defer` 保证**任何情况都回包**（`MysqlDao::UpdateFriendBack` 也 `catch` 了 `SQLException`），客户端 `tcpmgr.cpp` 的 `ID_UPDATE_FRIEND_BACK_RSP` 处理**总是 `emit sig_update_friend_back`**（含 JSON/DB 错误分支），`friendinfopage.cpp` 构造里 `sig_update_friend_back → slot_update_back_rsp` **只连一次**。→ 备注路径本身无论如何都会重新启用按钮。**所以"按钮卡死"只能是被某个模态对话框盖住点不动**——而 ChatDialog 里唯一的模态框就是加载用的 `LoadingDlg`（`setModal(true)`）。
- 真正的病根在**加载计数机制泄漏**：
  1. **双递减（double-decrement）**：`slot_load_chat_thread` / `slot_load_chat_msg` 里既有 `LoadingSession session(this)`（析构调 `endLoadingRequest()`），又在链式继续前显式调一次 `endLoadingRequest()`；而"下一个请求"是**直接 `emit` 不带 `beginLoadingRequest`**。于是每次回包被减两次、下一个请求的 +1 又缺失 → 计数在链式中途过早归 0、加载框闪关/计数错乱。
  2. **`offlineLogin()` 不复位**：`ChatDialog` 是 MainWindow 的常驻成员（`_chat_dlg` 跨登录/登出不销毁）。若一次聊天列表/消息加载被中断（断线/登出时加载还在途），`_loading_req_count` 残留 >0、模态 `LoadingDlg` 残留挂在屏幕上 → 整个 ChatDialog（含备注按钮）被阻塞（这就是"按钮卡死"）；下次登录 `loadChatList()` 再 `beginLoadingRequest` +1 叠在残留计数上，永远减不到 0 → `showLoadingDlg(false)` 永不触发 → **无限卡加载**。
- 双递减 + 不复位叠加：异常/中断路径最容易漏关，于是"退出再登录无限加载"稳定复现；而正常会话中只要加载曾被中断，模态框就会盖住备注按钮造成"改两次后卡死"的观感。

### 修法（计数严格 1:1，且登出必清）
- `chatdialog.h`：给 `ChatDialog` 加 `public resetLoadingState()`。
- `chatdialog.cpp`：
  - `slot_load_chat_thread` / `slot_load_chat_msg` 的链式继续分支：删掉显式 `endLoadingRequest()`，改为在发下一个请求前 `beginLoadingRequest()`（"当前回包由 LoadingSession 析构减、下一个请求 begin 计入在途"）。整条链 count 恒为 1，加载框既不提前关也不叠加。
  - `slot_load_chat_msg` 把 `LoadingSession session(this)` **提到函数最前**（覆盖 `_cur_load_chat==nullptr` 提前 return 等所有出口），删掉那里的显式 `endLoadingRequest()`。
  - `loadChatMsg()` 的 `_cur_load_chat==nullptr` 提前 return 删掉显式 `endLoadingRequest()`（它总在被 `slot_load_chat_thread` 的 LoadingSession 作用域内调用，计数由调用方析构统一减，不要再减）。
  - 新增 `resetLoadingState()`：`_loading_req_count=0; showLoadingDlg(false);`（关掉残留模态框）。
  - `loadChatList()` 开头先调 `resetLoadingState()`（防御：每次登录从干净计数开始，杜绝任何进入路径把计数叠到 >0）。
- `mainwindow.cpp` `offlineLogin()`：开头 `if (_chat_dlg) _chat_dlg->resetLoadingState();` —— 回到登录页前清掉可能残留的模态 LoadingDlg 与计数（覆盖主动登出/异地登录/心跳超时三种 disconnect 路径）。
- 不变量：`loadChatList` 仅由 MainWindow 登录调用、`loadChatMsg` 仅由 `slot_load_chat_thread` 调用（已 grep 确认），故"每个 begin 恰有一个 LoadingSession 析构配对"成立。
