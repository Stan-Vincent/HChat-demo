## 关键教训

### 1. 「返回值是指针还是值」只有编译器能查
本轮又踩了一次 protobuf 6.x：3.x 生成 public 字段（`msg.md5`），6.x 生成 inline getter（`msg.md5()`）。
静态自查（grep 函数名、括号配平）完全查不出来。

### 2. GateServer 的 GET 分发有个隐形陷阱
`LogicSystem::HandleGet` 里，**任何自己往 body 写内容并设置 status 的分支，都必须 `return true`**。
否则会 fallthrough 到精确路由表，动态文件名必然查不到 → 返回 false → 上层覆盖 status 并追加错误文本。

### 3. MySQL UPDATE 的 affected rows 语义
`UPDATE` 在新值==旧值时返回 0（除非开 `CLIENT_FOUND_ROWS`）。
凡是「用 affected rows 判断存在性」的逻辑，都得单独处理 0 行的情况。

### 4. Qt 信号做「请求-响应」多路复用的陷阱
`ReqId` 只能区分**模块**，区分不了**同一模块的第几次请求**。
只要同一模块可能并发/连续发多次请求，就不能靠共用信号分发 —— 必须按 reply 对象分发。

## 环境备忘
- 本机 MySQL/Redis 默认没起，GateServer 起来后会**静默退出**（只打印 config）。
  手工起：`mysqld.exe --defaults-file="C:/ProgramData/MySQL/MySQL Server 8.0/my.ini"`
  和 `redis-server.exe --port 6380 --requirepass 123456`
- **库里第一个用户是 uid=2，不是 uid=1**（写死 uid=1 的测试会误判成 bug）
- python urllib 请求 127.0.0.1 会被 `http_proxy` 环境变量劫持返回 502，
  测试要加 `no_proxy="127.0.0.1,localhost"`
- 用工具的 `run_in_background` 起服务端进程，**不要用 `(cmd &)`** —— 那样起的进程
  在工具调用结束时会被回收，表现为「服务刚起来就没了」
