## 文件上传限制评估（用户问"能不能放开到 300MB"）
当前三层冗余限制（都硬编码）：
- 客户端 `MessageTextEdit.cpp:156` = 20MB（拖入文件）
- 客户端 `uploadmanager.h:57/58` = 图片 10MB / 文件 20MB
- GateServer `HttpConnection.cpp:21` `body_limit(32MB)`（base64 膨胀 20MB→27MB 的余量）
- GateServer `LogicSystem.cpp:396` `MAX_UPLOAD_BYTES=20MB`（权威判定）
- ChatServer 不在此链路（只收发 URL）；`MAX_LENGTH=2048` 是聊天协议头上限，与文件无关。

**上传方式 = base64 塞 JSON 整包 POST**（`uploadmanager.cpp:121` `QString::fromLatin1(rawBytes.toBase64())`）。
300MB 文件膨胀账：原 300MB → base64 400MB → `QString::fromLatin1` UTF-16 **翻倍到 800MB** → QJsonValue 深拷贝 800MB
→ `toJson` 400MB（HTTP body 也 ≈400MB）。客户端峰值 ~1.5–2.7GB；服务端 dynamic_body 400MB + jsoncpp
`asString()` 400MB + `base64Decode()` 300MB = **每连接 ~1.1GB**。故"改常量到 300MB"= 客户端服务端同时 OOM。

**挖出两个隐藏问题（现在不炸只因 20MB 定能 <60s 传完）**：
1. ★ `HttpConnection.h:43` `deadline_` 在 accept 时构造定 60s，全代码**无 `expires_from_now` 刷新**；
   而 `async_wait` 是在 `async_read` 完成**之后**才 post（`HttpConnection.cpp:56`）→ 已过期的定时器立即
   触发关 socket。**任何传输 >60s 的上传都在和定时器赛跑**，客户端看到静默断连、无错误码。
2. ★ `HandleReq()` → `LogicSystem::HandlePost()` 是**直接同步调用**，无线程池派发；
   而 `AsioIOServicePool` 只有 **2 个 io 线程**（`AsioIOServicePool.h:26` size=2）。
   大上传的 jsoncpp 解析+base64 解码+写盘会占住其中一个线程数秒 = 队头阻塞，一半 HTTP 容量消失。

结论/建议：不建议直接放开。A 改常量 5 分钟但两人同时传就 OOM；C 折中（去 JSON 包装、服务端不解析 JSON
直接 base64Decode）约 1 小时，可舒服支撑 50–80MB；B 真流式（客户端 `QHttpMultiPart` 从 QFile 边读边发 +
服务端 `http::buffer_body` 边收边写盘）2–4 小时，才能承载 300MB。`deadline_` 那个坑与文件大小无关，建议单独先修。

## 群聊 6 条失败根因定位 + 修复（连接池 autocommit 泄漏）
- **复现即铁证**：在跑的 ChatServer(18:32 重编版) 上连跑两次 `group_chat_test.py`
  ——第一次 **9/9 全过**，第二次 **4/9**（同样的 6 条挂、错误码从 1014/1016 漂到 1011）。
  同二进制同库同代码、纯看借到连接池里哪条连接 = 典型竞态/状态污染，不是逻辑错误。
- **根因**：事务 DAO（`CreateGroupChat`/`AddGroupMembers`/`AddFriend`/`AddChatMsg`）都
  `conn->setAutoCommit(false)` 后只 `commit()/rollback()`，**从不把 autocommit 复原 true 就还池**。
  非事务读（`GetThreadType`/`GetGroupMembers`/`GetUserThreads`）借到这种"中毒"连接，
  autocommit=false 下第一条语句开 REPEATABLE READ 隐式事务、快照停在借连接瞬间 →
  读不到刚提交的群/成员 → "会话列表找不到群""成员校验失败"等偶发 1011/1014。
  （之前误以为是旧二进制/SQL bug，SQL 层用 thread 17 干跑已验证完全正确。）
- **修复（一处，覆盖全部）**：`ChatServer/MysqlDao.h` + `ChatServer2/MysqlDao.h` 的
  `returnConnection` 在 `pool_.push` 前加 `try{ if(con&&con->_con) con->_con->setAutoCommit(true); }catch(...){}`。
  这是所有 DAO 借/还连接的唯一出口。补丁脚本 `test/patch_autocommit_reset.py`（幂等、GBK+CRLF 安全、
  两 server 逐字节一致），已应用；`diff -q` 一致；`test/syntax_check.sh` 8/8 OK。
- ★ 该泄漏是全局稳定性隐患，不止群聊——所有走 `AddChatMsg`/`AddFriend`/`CreatePrivateChat` 的
  路径都偶发受影响。
