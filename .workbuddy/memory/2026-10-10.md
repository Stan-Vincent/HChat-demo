## ⚠️ ChatServer 帧协议格式（写测试/调试必备）
**帧头是 2+2 字节**：`HEAD_ID_LEN=2`（msg_id，`short` + `network_to_host_short`，大端）
+ `HEAD_LEN_LEN=2`（长度，大端），`HEAD_TOTAL_LEN=4`，`MAX_LENGTH=2048`。
Python 侧用 `struct.pack('>HH', msg_id, len(body))`，**不是 `>II`**。

例如明文 `123456` → 密文 `745230`。用 Python 做测试要 `xor_string(明文)` 后再发给 GateServer。

## Qt Creator 编译报 Error 1（post-link 拼接 bug）已修

### 现象
用户在 Qt Creator 里编译，输出：
`: error: [Makefile.Debug:350: bin/Hchat.exe] Error 1`
但 `bin/Hchat.exe` 能正常打开（因为链接其实成功了，exe 是新的，只是后置拷贝失败）。

### 根因
`Makefile.Debug:350` 是**后置拷贝命令那一行**（349 行才是真正的链接命令）。
原来在 `Hchat.pro` 里写了 **10 次 `QMAKE_POST_LINK +=`**（config.ini + 7 个 DLL + 3 个插件目录），
qmake 生成 Makefile 时把它们**用空格拼成一行**：
```
copy /Y "config.ini" "...\bin" copy /Y "libstdc++-6.dll" "...\bin" copy /Y ...
```
cmd 把后面所有命令当成 `copy` 的参数 → 语法错误 → **Error 1**。

**修复**：改成**一条** `QMAKE_POST_LINK +=`，命令之间用 `&&` 连接。

### ★★ 本项目编译环境的两个关键事实（踩过很多次了）
1. **Qt 的 MinGW 不带 `sh.exe`**（`D:\QT6\Tools\mingw1120_64\bin` 里没有）。
   `mingw32-make` 会先找 PATH 里的 `sh`；找不到才用 cmd 执行 recipe。
   - 从 **Qt Creator** 构建 → PATH 里没 Git 的 sh → **用 cmd** → `copy`（内建）可用
   - 从 **Git Bash** 里跑 make → PATH 里有 Git 的 `sh.exe` → **用 sh** → `copy` 找不到，报 **Error 127**
2. **MSYS 会把 `/Y`、`/E`、`/I` 当成 POSIX 路径转换掉**，导致 `xcopy` 报「参数无效」（**Error 4**）。
   实测：`xcopy 源 目标`（无开关）✅；`xcopy /Y ...` ❌；`xcopy -Y ...` ❌；`sh -c "xcopy /Y ..."` ❌
   只有 `MSYS2_ARG_CONV_EXCL="*" xcopy /Y ...` ✅（但那是 sh 语法，cmd 下不行）。

**结论**：`.pro` 的 post-link 按 **cmd 语法**写（`copy /Y` + `xcopy /Y /E /I`），
这样和 Qt Creator 行为一致。要在 bash 里复现同样的构建，必须先清掉 PATH 里的 sh：
```powershell
$env:PATH = "C:\Windows\system32;C:\Windows;D:\QT6\Tools\mingw1120_64\bin;D:\QT6\6.5.3\mingw_64\bin"
& "D:\QT6\Tools\mingw1120_64\bin\mingw32-make.exe" -j4
```
（用 PowerShell 工具执行，不要经 bash —— `cmd //c` 会被 MSYS 改写参数而失败）

## 【追加】登录后无限加载 + 程序卡死无法退出（23:00）

### 症状
登录成功后一直转圈（无限加载），整个窗口点不动，连标题栏的关闭按钮都无效，
只能强杀进程。

### 根因（4 层，逐层叠加）

**服务端 1：SQL 语法错误（我改图文消息字段时误删了一行）**
`ChatServer/MysqlDao.cpp` 的 `LoadChatMsg`：
```sql
SELECT message_id, ..., status
       AND message_id > ?      -- ← FROM chat_message WHERE thread_id = ? 整行丢了
ORDER BY message_id ASC
```
`prepareStatement` 抛SQLSyntaxErrorException → catch 返回 nullptr
→ `LogicSystem::LoadChatMsg` 置 `LOAD_CHAT_FAILED(1013)`。
**这是我自己改AddChatMsg 字段时弄坏的**，教训：改 GBK 文件的 SQL 片段后必须重读一遍确认。

**服务端 2：`load_more` / `next_cursor` 整个判断逻辑漏写**
SQL 用了 `fetch_limit = page_size + 1`（多取一条的惯用法），
但读完结果集后从来没写过 `page_res->load_more`，它一直是初始化的 `false`；
`next_cursor` 也永远停在传入的 `last_message_id` 不推进。
→ 消息超过 10 条时只加载前 10 条，再也翻不出来。

**客户端 3：模态加载框在所有错误路径上都没关（这才是「无法退出」的直接原因）**
`LoadingDlg` 是 `setModal(true)` 的 —— **模态框拦截窗口上所有输入，包括标题栏关闭按钮**。
只要漏关一次，用户就彻底失去交互能力。
而链式加载（load_more → 再拉一页 → 否则 loadChatMsg → 逐个会话拉消息）
中间有十几层，任何一层出错/提前 return，加载框就永久留下。

**客户端 4：tcpmgr 的 handler 在error != 0 时直接 return，不 emit 信号**
→ ChatDialog 根本不知道回包到了，计数永远配不平。

### 修法

1. 服务端补回 `FROM chat_message WHERE thread_id = ?`（两个 ChatServer 都改）
2. 服务端补回 `load_more` / `next_cursor` 判断（同上）
3. 客户端引入 **加载请求计数器** + RAII 守卫（`chatdialog.h` 的 `LoadingSession`）：
   - `loadChatList`/`loadChatMsg` 每发一个请求 `beginLoadingRequest()`（+1 并显示框）
   - 每个回包 handler 构造一个 `LoadingSession`，析构时 `endLoadingRequest()`（-1）
   - 计数减到 0 才 `showLoadingDlg(false)`
   - ★ 不能用「函数返回就关框」的朴素RAII：链路中间层会提前关掉框
4. `tcpmgr` 的两个 LOAD_*_RSP handler：**失败时也要 emit 信号**（load_more=false）
5. `showLoadingDlg(true)` 改成「已在显示就 return」，避免叠加多个模态框
6. `slot_load_chat_msg` 开头补 `_cur_load_chat` 判空（原来直接解引用）
7. `searchlist.cpp` 的 `waitPending` 补判空 + 构造函数初始化 `_loadingDialog(nullptr)`
   （原来 `_loadingDialog` 从没初始化过，`waitPending(false)` 会解引用野指针）

### 验证
写 `test/login_load_test.py` 模拟完整 TCP 登录链路（HTTP 拿 token → TCP 登录 1005
→拉线程列表翻页 → 逐会话拉消息）。
- 修前：所有会话 `error=1013`
- 修后：全部正常；造 32 条消息的会话 → **正确分 4 页取完（10+10+10+2），游标严格递增**

### 新增约定
- `MSG_CHAT_LOGIN = 1005` / `MSG_CHAT_LOGIN_RSP = 1006`（我一开始写成 1011，超时才发现）
- 客户端 `LoadingSession` 类**必须定义在 ChatDialog 类之后**（它要调 ChatDialog 的成员函数，
  写在前面会报 `invalid use of incomplete type`）
- 测试脚本登录要用 Redis 里现成的 `utoken_<uid>`：密码是 **Windows DPAPI 加密**的，
  明文 `POST /user_login` 会返回 `PasswdInvalid(1009)`

### 教训（自查方法论）
1. **编译器警告是最便宜的 bug 探测器**。`-Wunused-function` 直接指出了「崩溃处理器没被引用」。
   本轮 4 个 bug 里有 2 个是警告顺藤摸瓜找到的。
2. **`WINAPI` 这类宏后面必须有空格**，否则会和函数名粘连，且编译器不报错、只给个
   "defined but not used"。
3. **测试断言不要写死数据条数**——清掉测试数据后会误报 FAIL，让人以为代码坏了。
   改成运行时查库拿真实条数。
4. **链接 exe 前必须先停掉正在运行的同名进程**，否则 `LNK1104 无法打开文件`。
